## What exists in this App

**This App has no HTTP API of its own.** Its `lock_in+pid/nginx.conf` only serves `index.html` with
`Cache-Control: no-cache`; there are no `/lock_in+pid/lock`, `/osc`, `/calib` endpoints, no `c/lock` / `c/osc`
tools and no HTTP client (`control_finn.py`), unlike lock_in+pid_harmonic v2.3.15+. What exists:

| Way | Where it runs | Status |
|---|---|---|
| Python scripts of `lock_in+pid/py/` (`hugo.py` and the scripts built on it) | **on the Red Pitaya**, through SSH | the supported way for scripts; `lock_from_registers.py` tested on 2.0 |
| `resources/remote_control/control_hugo.py` | on a computer: runs the scripts of `py/` through SSH (`paramiko`) | **deprecated**, kept for specific cases; adapted to the lock control of v2.2.6, not re-tested on 2.0 |
| `POST /data` of the Ecosystem (the interface of the web page) | any computer | possible in principle, not provided nor tested for this App ([below](#the-post-data-interface-of-the-ecosystem)) |

The App must be **loaded** (FPGA image of this App in the PL, e.g. by opening its page once or with
`http://rp-XXXXXX.local/bazaar?start=lock_in+pid`). Do not run the scripts while another App is loaded: they
access the FPGA addresses directly through `/dev/mem`.

The scripts are installed with the App in `/opt/redpitaya/www/apps/lock_in+pid/py/` (Python 3, root). Log in with
`ssh root@rp-XXXXXX.local` (the `upload_app.sh` of the package installs an SSH key, see
[Devel.md](Devel.md#installing-on-the-board)). Running them creates `py/__pycache__/` on the board, which is harmless
([`lock_capture.md`](../lock_in+pid/doc/lock_capture.md) §5).

## Scripts on the board (`py/`)

### `hugo.py`: registers by name

`py/hugo.py` defines two objects with the register tables of the FPGA (generated by
`resources/config_tool.py`, `# [REGSET DOCK]`):

- `li`: lock module, base 0x40600000, 111 registers (`fpga_lock_in`, names and indices of [FPGA.md](FPGA.md#lock-module-0x40600000));
  helpers `freeze()` / `unfreeze()` (`read_ctrl[0]`), `start_clk()` / `stop_clk()` (`read_ctrl[1]`).
- `osc`: oscilloscope, base 0x40100000, registers 0..19 (`fpga_osc`); helpers `reset()`, `set_dec()` / `dec()`
  (1, 8, 64, 1024, 8192, 65536, 524288), `trig_now()`, `trig_ext()`, `trig_ChA_rise()`…, `start_trigger()` (writes the
  2.0 trigger unlock 0x94 and then `TrgSrc`), `acq_done()` (`conf` bit 4 on the 2.0 FPGA), `get_chs()` /
  `get_curves()` (16384 samples of each channel, 14-bit, rotated so that the first sample is the oldest).

Each register is read or written with `.val()`; signed registers are converted (`fpga_reg.val()`, mmap of
`/dev/mem`):

```python
# on the Red Pitaya, in /opt/redpitaya/www/apps/lock_in+pid/py
from hugo import li, osc

li['oscA_sw'].val(1)            # scope channel 1 = in1
li['pidA_kp'].val(-500)         # signed 14-bit
print(li['lock_status'].val())  # read only
li.show('in1')                  # print name:value
li.freeze(); x = li['X_28'].val(); y = li['Y_28'].val(); li.unfreeze()   # X and Y of the same instant
```

### `lock.py` and `osc.py`: command line access

```bash
cd /opt/redpitaya/www/apps/lock_in+pid/py
./lock.py                       # all lock registers, one "name:value" per line
./lock.py pidA_kp               # one register
./lock.py pidA_kp -500          # write and print
./lock.py in1 in2 error         # several
./osc.py Dec                    # same for the scope registers (0..19)
./osc.py Dec 1024
```

These are the commands that `control_hugo.py` runs through SSH.

### `lock_from_registers.py`: close and release a lock

Closes the lock writing only FPGA registers and reads its state (v2.2.6, from lock_in+pid_harmonic v2.3.14). The
FPGA runs the lock sequence by itself; nothing has to be copied back. Usage (from its docstring and
[`lock_control.md`](../lock_in+pid/doc/lock_control.md) §5):

```bash
./lock_from_registers.py --status                                   # decode lock_status
./lock_from_registers.py --trig time --time 16.58ms --set pidA,pidB # arm, wait for the lock, report
./lock_from_registers.py --trig level --level 5085 --sw 0 --rise --set pidA
./lock_from_registers.py --trig both --time 10ms --level 0.5V --sw 0 --fall
./lock_from_registers.py --now --set pidA,pidB                      # lock right now
./lock_from_registers.py --release                                  # back to the manual enables
./lock_from_registers.py --trig time --time 16.58ms --set pidA --force   # release and arm again
```

- Sequence: `lock_trig_time` (0x34), `lock_trig_val` (0x30), `lock_trig_sw` (0x38); `lock_control` with bits 1-0 =
  00, the manual enables and the trigger configuration; then bit 1 = 1 (arm) or bit 0 = 1 (lock now); then it polls
  `lock_status` until `locked` or timeout.
- If the lock is already LOCKED (or ARMED) with the same request, nothing is written (a new request would open the
  loop for a few ms); `--force` re-arms anyway.
- `--sw` is the `lock_trig_sw` value of this App: 0 error, 1 X, 2 Y, 3 F1, 4 F2, 5 F3, 6 sqX, 7 sqY, 8 sqF,
  9 signal_i, 10 ramp_A, 11 aux_A, 12 in1, 13 in2, 14 in1−in2, 15 pidA_out.

Tested on RP2 with v2.2.6 and the page open: `--release`, `--trig time --time 16ms --set pidA` (ARMED → LOCKED in
0.05 s), `--status`, `--now`, `--time 100ms` (stays ARMED); the page followed OFF / ARMED / LOCKED and the `set_*`
in ≤ 1 s, with 0 POST (`testAgent.md` 2026-10-10 09:48).

**A confirmar:** the trigger values written by the script (0x30, 0x34, 0x38) are not shown in the fields of the
page, and if a lock parameter is then changed in the page the controller rewrites them with its own copy (on the
board the lock then fired at 18 ms instead of 100 ms). Do not change lock parameters in the page while a lock armed
from Python is waiting, or re-run the script after the change. See [Structure.md](Structure.md#lock-control).

### Oscilloscope: `osc_trig.py` and `osc_get_ch.py`

```bash
./osc_trig.py -s now -d 8               # arm with trigger "now", decimation 8, wait for the end
./osc_trig.py -s ext -t 20              # external trigger (the lock trigger, trig_sw), timeout 20 s
./osc_trig.py -s chAup -v 1000 -p 8192  # ch A rising at 1000 counts, 8192 samples after the trigger
./osc_get_ch.py > data.csv              # "index,chA,chB" for the 16384 samples (-b: binary, big-endian int16 pairs)
```

`osc_trig.py` resets the scope, sets the decimation (`-d`: 1, 8, 64, 1024, 8192, 65536; 524288 is not in its list),
thresholds / hysteresis / `TrgDelay`, calls `osc.start_trigger()` and waits for `conf` bit 2 (trigger) and then for
the end of the acquisition (`acq_done()`, `conf` bit 4: on the 2.0 FPGA `TrgSrc` keeps bit 5 after a trigger and
never reads 0; fixed in v2.2.6). It prints `success`, `timeout` or `memory read error`.

**A confirmar:** `osc_trig.py`, `osc_get_ch.py` and `data_dump.py` were not run on the board in v2.2.x. While the App
is loaded, the scope worker of the C controller keeps acquiring on the same scope (in Auto even with no page open);
a script that arms the scope competes with it. In lock_in+pid_harmonic this is solved by putting the controller in
Single through `POST /data` before acquiring ([below](#the-post-data-interface-of-the-ecosystem)); in this App it
was not tested. Using the Single mode of the page (or Stop) before acquiring from a script is the safe option.

### `data_dump.py`: stream register values

`py/data_dump.py -s <ip> -p <port> --params error ctrl_A ...` samples the named lock registers on the board
(period `Dtime` = 2 ms) and sends them over TCP with `nc` to `<ip>:<port>`. On the computer receive with
`nc -l -p 6000 > file.bin` (or `control_hugo.py` `start_streaming()`, which does both) and decode with
`resources/remote_control/read_dump.py`. This is a slow logger of register values, not a stream of the scope (this
App has no scope streaming). Not tested on 2.0 (a confirmar).

## SSH client `control_hugo.py` (deprecated)

`resources/remote_control/control_hugo.py` (with `config_RP.py`, `example.py`, `example_calibration.py`,
`process_osc.py`, `read_dump.py`) is the original remote control of this App: a Python class on the computer that
connects through SSH (`paramiko`) and runs the scripts of `py/` on the board. It is **deprecated** and kept for
specific cases; for new scripts run Python on the board ([above](#scripts-on-the-board-py)). Requirements on the
computer: `numpy`, `paramiko`, `requests`, `bs4` (+ `lxml`), `matplotlib` (optional), and `nc` for streaming.

```python
from control_hugo import red_pitaya_app

rp = red_pitaya_app(AppName='lock_in+pid', host='rp-XXXXXX.local', port=22,
                    password='root', filename='test.npz')   # AppName must be given: the default is 'lock-in_pid'
rp.lock.pidA_kp = -500            # writes through py/lock.py
print(rp.lock.get('in1'))         # reads one register
rp.osc_trig_fire(trig=6, dec=8)   # arm the scope (external trigger), py/osc.py
rp.get_curv(log='peak')           # read both channels (py/osc_get_ch.py) + all registers
rp.plot(); rp.save()
```

| Method | What it does |
|---|---|
| `rp.lock.<reg>`, `rp.lock.get()`, `rp.lock.set()`; `rp.osc.…` | registers by name through `py/lock.py` / `py/osc.py` |
| `pidA_enable()`, `pidB_enable()`, `ramp_enable()` | manual enables (bits 3, 2, 4 of `lock_control`) |
| `launch_lock()`, `lock_now()` | lock request: writes bits 1-0 = 00 and then the request bit (0→1 edge; fixed in v2.2.6, they always failed before) |
| `release_lock()`, `lock_status()` | release (bits 1-0 = 00) and decoded `lock_status` (v2.2.6) |
| `lock_control`, `lock_control_trigger_config`, `set_lock_control_trigger_config()` | read / write the configuration bits and the trigger registers |
| `osc_trig_fire()`, `get_curv()`, `plot()`, `save()`, `load()` | scope acquisition and data handling |
| `counter_*()` | tick counter (`read_ctrl[1]`, `cnt_clk*`) |
| `start_streaming()`, `stop_streaming()` | register logger with `py/data_dump.py` + `nc` |
| `get_adc_dac_calib()`, `set_adc_dac_calib()` | read / write the calibration with `/opt/redpitaya/bin/calib` |

Known problems of the SSH version (reported to devAgent, not fixed): the default `AppName` is `'lock-in_pid'` (the App
folder is `lock_in+pid`); `loadApp()` runs `py/load_app.py` and `osc_trig_fire(wait=True)` runs `py/wait_trig.py`,
which do not exist; `osc_trig_fire()` writes `TrgSrc` with `py/osc.py` without the 2.0 trigger unlock (0x94), so on the
2.0 scope it may not trigger again after a first acquisition unless the controller unlocked it (a confirmar); its
decimation list lacks 524288; the docstring of `get_curv()` says the time step is `8 ns · 2**dec` (it is `8 ns · dec`).

## Recipes

All on the board (`ssh root@rp-XXXXXX.local`, `cd /opt/redpitaya/www/apps/lock_in+pid/py`), with `python3`.

**Configure the harmonic lock-in** (input in1, 49.6 kHz, X/Y/F1 filter 262 µs order 2, gain ×32, modulation on OUT2):

```python
from hugo import li
li['signal_sw'].val(0)           # in1
li['gen_mod_hp'].val(0)          # 49.603 kHz
li['lpf_F1'].val((2 << 4) | 1)   # order 2, tau index 1 (262 us)
li['sg_amp1'].val(5)             # x32 for Xo, Yo, F1o
li['out2_sw'].val(4)             # OUT2 = cos_ref (to modulate the system outside the board)
li.freeze(); X, Y = li['X_28'].val(), li['Y_28'].val(); li.unfreeze()
print('X = %.4f V, Y = %.4f V' % (X / 2**11 / 8192, Y / 2**11 / 8192))
```

**Configure the square lock-in** (independent square reference of 1.25 MHz: period = 2·(`gen_mod_sqp`+1) ticks =
100 ticks → `gen_mod_sqp` = 49):

```python
li['gen_mod_sqp'].val(49)        # period 2*(49+1)*8 ns = 800 ns (1.25 MHz)
li['lpf_sq'].val((2 << 4) | 8)   # order 2, tau index 8 (131 us)
li['sg_amp_sq'].val(0)
```

**Configure PID A and the ramp** (scan ±5000 on OUT1, PID A on the error):

```python
li['out1_sw'].val(12)            # OUT1 = ctrl_A
li['ramp_low_lim'].val(-5000); li['ramp_hig_lim'].val(5000)
li['ramp_step'].val(400)         # 64.16 ms
li['ramp_enable'].val(1)
li['error_sw'].val(2)            # error = Xo
li['pidA_sw'].val(0)             # PID A input = error
li['pidA_PSR'].val(3); li['pidA_kp'].val(-500)   # -500/1024
li['pidA_ISR'].val(8); li['pidA_ki'].val(-20)    # tau_i = 537 ms / 20
```

**Close and check a lock**: `./lock_from_registers.py --trig time --time 16.58ms --set pidA`, then
`./lock_from_registers.py --status` and `./lock.py error_mean error_std` (mean in counts = `error_mean / 2^18`,
std as in [FPGA.md](FPGA.md#lock-in-amplifiers)); release with `--release`. The values above are examples; a real lock
with this App was not validated on the current bench (a confirmar).

If the web page is open, the controller rewrites all the lock registers with the values of the page on the next
change made in the page; set the same values in the page, or do not touch it while a script controls the App.

## The `POST /data` interface of the Ecosystem

The web page talks to the C controller with `POST /data` (JSON `{"datasets":{"params":{"name":value,…}}}`), where the
names are those of the parameter table of `src/main.c` (e.g. `lock_pidA_kp`, `lock_ctrl_aux_launch_lock_trig`,
`trig_mode`); the controller clamps each value to its `min`/`max` and writes the registers (`rp_set_params()`). A
program could do the same, but **this is not provided nor tested for this App**. What was learned on the same
Ecosystem with lock_in+pid_harmonic ([its Remote.md](https://github.com/marceluda/rp_lock-in_pid_h/blob/devel2.0/doc/Remote.md)):

- `trig_mode` = 2 (Single) stops the acquisitions of the controller; 0 gives Auto back.
- Use only `POST /data` (a `GET /data` while another 2.0 App is loaded crashes the nginx worker), with the body in the
  same TCP segment as the headers (`curl` does so; Python `requests` sometimes does not), and bodies of at most ~600 B.
- **Every `POST /data` leaves a connection in CLOSE-WAIT in the nginx of the board** (OS 2.04-35); after about 1000 the
  web server stops answering until `systemctl restart redpitaya_nginx`. The web page itself is affected: testAgent
  found ~165 CLOSE-WAIT left on RP2 after the tests of v2.2.6 (`reportes/lock-in_pid.md`).

## Coexistence with the web page

- The page and the scripts can run at the same time: the page shows the lock state written from Python
  (`lock_status`, `lock_control`) on every poll, without sending anything.
- The controller writes **all** the lock registers (except `lock_control`, which is written only when the user
  changes it) every time a lock parameter changes in the page; values written by scripts in other registers are then
  overwritten. They are read back into the page only with complete acquisitions.
- Opening the page in a new tab sends `lock_now = launch = 0` (transient lock requests are never restored), which may
  release a lock held from Python (seen in lock_in+pid_harmonic; a confirmar here).
- The scope is shared with the scope worker of the controller ([above](#oscilloscope-osc_trigpy-and-osc_get_chpy)).
